# Expression: how the site speaks

更新: 2026-11-06。対象: Home、機能（`/features`）、連携（`/integrations`）、導入相談（`/support`）、
コミュニティ（`/community`）、About（`/about`）、ブログ一覧、Privacy。
文言の正本は `shumoku-site-copy.ja.md`（サイト計画のコピー案）。由来と思想の正本は製品リポジトリの
`docs/ORIGIN.md` と `docs/PHILOSOPHY.md`。ここではそれらを複製せず、画面表現への写像だけを記録する。

## 由来から導いた三つの態度

| 由来・思想 | 画面での態度 |
| --- | --- |
| 撞木釘は喚鐘を「静かに支える」基点。羽は「派手に主張するため」ではない | 静けさ。装飾的な動き・グラデーション・粒子背景を置かない。強い色は緑一色だけ |
| 図は構造を作らず、すでにある構造に「輪郭を与える」「しるし」 | 主役は図そのもの。実画面と、公開パッケージが実際に生成した図だけを見せる。架空の画面は描かない |
| Readable を最優先。同じ地図を熟練度に応じて深く読める | 一つのセクションは「主張 → 証拠（画面・図・表）→ 次の一歩」。全体を見せてから細部を拡大する |

これはプロジェクトの造形判断であり、由来の文章を画面に載せることではない。由来そのものは About に置く。

## デザインと伝達の配分

- **伝達が先、デザインは図の語彙から。** 新しい装飾モチーフを発明しない。サイトの視覚的な個性は、
  製品の図がもともと持つ語彙（機器の枠、黒地のポートタグ、接続線、使用率の色）から取る。
  ポートタグ型のラベルは「機器:ポート」のように実際に図の要素を指す時だけ使う。
- **証拠は本物だけ。** Hero と事例は JANOG57 NOC の実画面。「構成をデータで扱う」の図は、
  `@shumoku/core` と `@shumoku/renderer-svg` がビルド時に YAML から生成した SVG で、手描きしない。
- **画像がない所は空けておく。** 欲しいが素材がない箇所は `Frame` の `label` で枠と用途だけを示し、
  画面を捏造しない。公開前に差し替えるか、枠ごと外す。
- **動きは二つだけ、どちらも一度きりか操作に応じて。** 接続先ポートの切替で図が差し替わる瞬間と、
  Hero の二行目がブランドの緑の輪郭線から左へ塗りで満ちる一度きりの表現（「すでにある構造に輪郭を与える」）。
  塗りの境目は `@property` で登録した変数で動かすので、非対応のブラウザーや `prefers-reduced-motion`
  では最初から塗られた状態になる。常時動く表現は使わない（文字に点を流す案は、点の密集が
  集合体恐怖症を思わせたため撤回した）。
- **配色・文字・余白は既存の基盤を使う。** `color-system.md` の緑＋暖色ニュートラル、`ui.css` の
  間隔トークン、`site-container`、`LinkButton`。ホームの画像カードは `ui-kit.md` の 16/10/6px 入れ子。

## レイアウトの基準

幅・段・余白は `src/routes/website.css` の変数と 12 列のページグリッドだけで決める。部品は独自の
最大幅や余白を持たない（初版は 44rem、52rem、42rem などを部品ごとに持ち、文章幅が 704px、447px、
832px、1120px と揃わなかった）。

### 列の位置

- 2列のセクションは文章が 1〜5 列、証拠が 7〜12 列で、上端を揃える。Hero の本文も 7 列目から始まる。
- 1列のセクションは文章が 1〜7 列（読みやすい行長）、証拠は全幅。導入手順は 1〜9 列。
- コミュニティの写真は列の線 1・5・9 に乗り、文章はその2列目の線（5 列目）から始める。
- ブログ一覧は 1〜9 列（サムネイル 3 列、本文 6 列）。Privacy の本文は 1〜7 列。

### 列は `subgrid` で受け取る

`.layout-grid` がページに一組だけ列を持ち、`.layout-sub` が `subgrid` で何段でも下へ渡す。部品は
`grid-column: span 4` のように自分の幅だけを書く。親が何列あるかを部品は知らない。

- 部品の中に列数を書き直さない（以前の `repeat(6, …)`、`repeat(9, …)`、`repeat(3, …)` は親の列数を
  部品が知っている状態で、親が変わると壊れた）。列を計算する変数（旧 `--layout-col`）も置かない。
  `100vw` から求めていたのでスクロールバーの幅だけずれていた。
- ページグリッドと、列を使う要素の間にある要素は、すべて `.layout-sub` にする。
- `.span-text` などの配置クラスは、全幅の（12 列を受け取った）`.layout-sub` の直下でも使える。

### ブレークポイントはページに一つ

`website.css` の 850px だけがグリッドのブレークポイントで、これより狭いと列は 1 本になる。
`.layout-sub` はそこで flex の縦積みになり、部品が書いた `span n` や `8 / -1` は無視されるので、
部品は何も書かなくても縦に並ぶ。

- 850px 以下では `.layout-grid` と `.layout-sub` がクエリコンテナーを兼ねる。部品が狭い幅で別の組み方を
  するときは `@media` ではなく `@container (…)` で自分の幅を読む（`@container (min-width: 37rem)` で
  2 列など）。その中で `display: grid` を指定し直す。
- 850px より広い間はコンテナーにしない。サイズコンテナーは独立した整形コンテキストになり、`subgrid` に
  なれない（列の受け渡しが切れる）。だからこの `@container` は広い幅では常に偽になる。
- 列を受け取らない末端の部品（`CommandPanel`、フッター、告知バー）は、常に自分をコンテナーにしてよい。
- 例外はヘッダーの二つの `@media` だけ。1100px のメニュー切替は七つの行き先の幅から決まる値で、ページの
  列とは無関係。850px のロゴ切替は `<picture><source media>` がビューポートしか読めないため同じ値に揃える。
- 記事ページ（`ArticleBody`、`LinkCard`）と Playground、UI プレビューはこの範囲の外で、自前の
  `@media` を残している。
- `subgrid` は 2023 年以降の主要ブラウザーで使える。非対応のブラウザー向けの代替は用意していない。

### 画像の枠は `Frame` だけが持つ

比率、切り抜き、線、角丸は `src/lib/product/Frame.svelte` だけが決める。トークンは `--layout-media-ratio`（3:2）と
`--layout-media-radius`（8px）の各一つ。

- 画像は枠いっぱいに置き、線は `::after` で上に重ねる。線の分だけ画像が内側へずれないので、
  見えている画像の端がそのまま列の線に乗る。
- `variant`: `shot`（切り抜く。題名などが切れる画像は `position` で残す側を指定する。ダッシュボードは
  `top left`）、`diagram`（白地に図全体。キャプションは枠の中）、`logo`（中央に小さく）。
- `label` で素材待ちの枠、`children` で同じ枠に別の中身（`BeforeAfter`）。`ratio="natural"` は画像自身の比率
  （Hero、図）。`bare` は線なし（ブログのサムネイル）。
- コミュニティのモンタージュだけは写真の組み合わせそのものが構成なので、比率（16:9、狭い幅で 4:3）を
  自分で持つ。角丸は同じトークンを使う。

### 親は子の中身を触らない

`:global` で子の内部を指定しない。部品のスタイルは部品に置き、ページは部品を並べるだけにする（Home の
前後比較は `BeforeAfter`、導入手順は `Steps`、監視ソースは `SourceList`、三つ並びは `Columns` と
`Column`）。残してよい `:global` は `<enhanced:img>` が生成する `<picture><img>` と、記事本文のように
Markdown から生成された要素だけ。

### 生成した図はファイルで配信する

図はビルド時に `/diagrams/<名前>.svg`（`src/routes/diagrams/[name].svg/+server.ts`）へプリレンダーし、
`<img>` で読む。HTML に直接入れていた頃は、図のたびに `g-router` などの id が最大 13 回重複し、同じ SVG が
hydration データにも入って Home の HTML が 384KB あった（今は 47KB）。ページのデータに渡すのは
レイアウトが動かないようにするための縦横のサイズだけ。

- `<img>` の中へ CSS は届かないので、変わったポート名の緑は生成時に焼き込む（`highlightPortLabel`）。
  Ethernet1 と Ethernet2 は別のファイルで、切替は `src` を替える。
- このルートは `sitePages` に入れない。サイトマップとナビゲーションはそこから作るので、どちらにも出ない。

### 揃っていることはテストで守る

`bun run check` の最後に `scripts/check-layout.ts` が、ビルドした `/ja` と `/en` の 8 ページを
ヘッドレス Chrome で測る。依存もブラウザーのダウンロードも足さない（CI の ubuntu-latest には入っている。
別の場所なら `CHROME_BIN`）。

- 1280px: 見えている画像そのもの（包む箱ではなく、`object-fit: contain` なら描かれた部分）と、枠、表、
  一覧の左右の端が、ブラウザーの計算した 12 列の線に乗っているか。文章は左端だけ。誤差は 0.5px で、
  1px の線で押された画像も検出する。
- 1280px: `.span-*` と Hero の本文が、上の「列の位置」のとおりの列にあるか。
- 1280、900、375px: ページ全体が横にスクロールしないか。読み込めない画像も失敗にする。
- 線から外れてよいものはテストの `exceptions` に理由つきで書く（行内のロゴ、枠の中の図や文字）。どこにも
  当たらなくなった例外も失敗にして、一覧を古くしない。増やす前に、内容で決まる位置なのかを考える。

## セクションの型と見た目

2026-11-04 に約40サイトを調べて決め直した（構成はテキストで、見た目はスクリーンショットで比較）。
初版の「全セクション同じ型・背景の帯の交互・厚い枠」は、強弱のない生成サイトの見え方になったため撤回した。

- **一文のすぐ下に本物の出力。** MRTG や Smokeping が説明の直下にグラフを置くのと同じ考え方。
  Hero は JANOG57 の実画面、その直後に YAML と生成図、続けて公開パッケージで描いた図の一覧
  （`src/lib/product/gallery/`）。ネットワーク可視化の競合で Hero にトポロジー図を置く例はなかった。
- **飾りで強調しない。** 2026-11-04 に impeccable の批評手順（デザインレビュー）と frontend-design の
  禁止リストで検査し、生成サイトに見える原因として次を外した: 見出し上の線と四角の印（文字のない
  見出し上ラベル）、Hero 見出し後半の緑（一部だけ色を変える見出し）、ボタン下の緑の点つきリリース文
  （「Live」風のバッジ、最近の動きと重複）、等幅の日付、緑の下線と緑の線のボタン（色が行動の目印で
  なくなる）。最新リリースは「最近の動き」にだけ載せる。
- **色は「押すべきボタン」だけ。** 緑は塗りの主ボタン、フォーカス、リンクのホバーに限る。副ボタンは
  中立色の線、文中リンクは石色の下線。強弱は見出しの太さと大きさ、本物の図で付ける。
- **日本語の見出しは組版で立たせる。** 書体はそのまま、日本語の h1〜h3 に `palt`（仮名・約物の詰め）と
  `text-spacing-trim` を掛け、欧文用の負の字間はやめる。Hero だけは助詞を 0.72em に小さくして名詞を
  立てる（コピーでは `ネットワーク[にも]、` のように角括弧で示す）。
- **場面の画像は本物で埋める。** 配線変更の前後は、YAML のデモと同じビルド時の図を並べ、変わった
  ポート名だけ緑にする。同じ行き先のボタンは一つにする（Playground は図の一覧の後だけ）。
- **日付つきの動き。** ブログ・リリース・イベントを素直な一覧で並べる（Nmap、JANOG 型）。
  リリースは `src/lib/content/activity.ts` に手で追加し、記事は自動で入る。
- **実際のコマンド。** README のとおりの CLI と Docker コマンドをコピーボタン付きで見せる。
- **正直な範囲。** FAQ で「NetBox や監視ツールの代わりではない」と書く。ロゴの壁や出典のない数字は置かない。
- **形を変える。** 図、一覧、コマンド、質問と答え、日付の一覧と、隣り合うセクションで形を変える。
  区切りは背景の帯ではなく罫線。枠は 1px の線だけ。見出しは主要な3つ（データ、場面、試用）だけ大きくする。
- **声。** 導入相談は「私たちが手伝います」と一人称で一文。由来は Home に書かず、OSS の節から About へリンクする
  （末尾に一行で置いた由来は唐突だったため外した）。

足すかどうかの基準は「読む人の判断に必要か」だけ。

## 導入相談とコミュニティ

文言は `src/lib/content/pages.ts`（コピー案の「導入相談」「コミュニティ」）。

- 導入相談は、説明（左）と支援内容の罫線リスト（右）、問い合わせ、コミュニティへの案内の三つだけ。
  ページの主な行動は問い合わせのメールなので、塗りのボタンはそこだけ。旧ページのアイコン付き
  カードと、中央から線が伸びる「一緒に作る」の図（中身のないロードマップを含む）は外した。
  `/support#enterprise` の既存リンクは、支援内容のセクションの id で受ける。
- コミュニティは、Meetup #1 の写真のモンタージュ（本物の人の姿）を残し、その間の文章をコピー案の
  「質問と情報交換」と Meetup に置き換え、見出しと本文を Home と同じ列（1〜5 / 7〜12）に揃えた。
  脆弱性の報告先と行動規範は、旧ページから引き継いだ。

## About

カードで言い換えていた由来を、製品リポジトリの `ORIGIN.md` と `PHILOSOPHY.md` の言葉（一人称）で読み物として
組む。聖書の引用は About に載せず、全文は `ORIGIN.md` へリンクする。英語版は私たちの訳で、原文は日本語のみ。

## ブログ一覧、Privacy、Connect

ブログ一覧と Privacy も `.layout-grid` に乗せ、左端をロゴや他のページに揃えた。記事ページの中央寄せの読み物の列と、Connect の中央寄せの狭いリスト（スマホで QR から開く用途）は、
それぞれの目的に合うので変えていない。
